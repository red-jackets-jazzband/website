# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- **Local dev server**: `hugo serve` (serves at http://localhost:1313)
- **Build**: `hugo` (outputs to `public/`)
- **Link checking**: `pip install linkchecker && linkchecker public/index.html` (run after `hugo`)
- **Lint everything**: `npm run lint` — runs the six checks below in sequence; `--max-warnings 0` on the JS step means a `complexity`/`sonarjs/cognitive-complexity` *warning* fails the build exactly like an error would, so cyclomatic/cognitive complexity is already a hard gate, not just advisory.
  - `npm run lint:js` — ESLint 10 flat config, strict, covers all of `static/script/**` + `scripts/**` + `tests/**`; vendored `abcjs*` / `tonal*` bundles and any `*min.js` file (which also covers `lamejs-1.2.1-min.js`) are ignored.
  - `npm run lint:css` — Stylelint over `assets/css/**/*.css` (see below).
  - `npm run lint:dup` — jscpd copy-paste/duplication detection over `static/script`, `assets/css` and `tests` (see below).
  - `npm run lint:types` — `tsc -p tsconfig.lib.json`, type-checking `static/script/lib/**` (see below).
  - `npm run lint:abc` — [scripts/lint-abc.js](scripts/lint-abc.js) runs every `static/songs/*.abc` file through the real `abcjs` npm package's `ABCJS.parseOnly` (the same parser the `/songs/` page uses to render a tune, run headlessly in Node — no DOM needed for parsing) and fails on two classes of problem: any parser warning (unknown character, malformed header, bad note syntax, ...), and any **bar whose notated duration doesn't match the tune's `M:` meter** — a dropped rest or mistyped note length is otherwise invisible until someone notices the sheet or playback sounds off, and abcjs's own parser doesn't check it. The bar-length check walks the parsed tune's per-voice element stream itself (summing `duration`, scaled by `tripletMultiplier` between a `startTriplet`/`endTriplet` pair, resetting at each `el_type: "overlay"` voice-overlay marker) rather than shelling out to a separate tool (`abc2midi` from the `abcMIDI` suite does the same check, but is far noisier on this corpus — it doesn't recognize this project's jazz chord extensions like `7#5`/`mØ` and has its own tie-handling quirks, so it'd need a real suppression list before it could gate CI). A bar is only flagged if it's **overfull** (too many beats — always wrong), or **underfull and interior** — a short first bar (pickup/anacrusis) or a short bar immediately before/after a `P:` part change is normal lead-sheet convention and deliberately exempted, as is a tune/voice's closing bar. Catches a broken or malformed transcription as a CI failure instead of a blank/garbled staff or a rhythm that's quietly wrong. `abcjs` here is a real devDependency (pinned to the same `6.7.0` line as the vendored browser bundle `static/script/abcjs_midi_6.7.0-min.js`) purely for its parser; the site itself keeps using the vendored classic-script bundle — this package never ships to `public/`.
  - `npm run lint:setlists` — [scripts/lint-setlists.js](scripts/lint-setlists.js) runs every `static/setlists/*.txt` file (skipping the `index_of_setlists.txt` manifest itself) through the real `parseSetlistFile` and fails if it returns any `warnings` — a line inside the song list that didn't parse as a song, a divider, a comment, or a note continuation. Exists because the markdown-ish setlist format (see **Setlists tab** below) disambiguates "song line" from "free text" and "old syntax" by shape-sniffing, and a line that sniffs wrong used to fail silently — either vanishing, or (before a parser fix) being misread as a bogus, 404-ing song entry — with nothing to catch it before someone noticed a setlist looked wrong on the live site. `parseSetlistFile` itself never throws on this; `warnings` is the hook a caller can act on, and this script is the one place that does.
- **Unit tests**: `npm test` (Node's built-in test runner: `static/script/**/*.test.js` colocated with the code + `tests/**/*.test.js`; DOM-touching modules run under jsdom)
- **Dependency audit**: `npm run audit` (`npm audit --audit-level=high`) — also runs in CI as its own step, after lint and test.
- **SEO lint**: `npm run lint:seo` — [scripts/lint-seo.js](scripts/lint-seo.js) audits the *built* `public/` output (not the templates), so it must run after `hugo`, not as part of `npm run lint`; that's why it's a CI step of its own in the `build` job (after the Hugo build, alongside `linkchecker`), not one of the five checks `npm run lint` chains. It walks every generated `.html` file (skipping Hugo's own alias-redirect stubs, detected by their `http-equiv=refresh`) and checks: exactly one `<title>` (≤70 chars) and one meta description (50–160 chars); exactly one `<h1>`; `<html lang>` matches the page's actual language (the regression class this catches: Hugo's `default` template func is `default DEFAULT GIVEN` — passing a non-empty string literal as `GIVEN` makes it win unconditionally, which is exactly how `themes/split/layouts/_default/baseof.html` used to stamp `lang="en-US"` on every page regardless of language before the [dfetch patch](patches/themes-split.patch) fixed the argument order); every `<img>` has non-empty `alt`; the canonical link and `og:url` both equal the page's real permalink (not the site's `BaseURL`, which was the previous bug); `og:title`/`og:description`/`og:type` are present; meta robots doesn't say `noindex`; every page that has translations carries hreflang alternates for all of them; and no two pages share an identical meta description. `public/robots.txt` (Hugo-generated via `enableRobotsTXT = true` + [layouts/robots.txt](layouts/robots.txt)) and `public/sitemap.xml` are checked for existence too. All tag/attribute lookups are manual `indexOf` scans, never a `"[^"]*"`-shaped regex, for the same reason given in the "Regexes that scan for a closing delimiter" note below.

The site itself has no build step beyond Hugo — it's a pure static site, and `package.json`/`node_modules` exist purely as **dev tooling** (lint + unit tests + a jsdom harness for the vanilla JS), never as part of the Hugo build or the GitHub Pages deploy.

### Keeping SonarCloud clean

The project is scanned on SonarCloud (https://sonarcloud.io/dashboard?id=red-jackets-jazzband_website). Outbound network access to sonarcloud.io is blocked from this sandbox, so there's no way to pull live findings from here — `npm run lint` is the authoritative local signal instead, built from tools that check for the same classes of problem SonarCloud's own analyzers do:

- **JS correctness/security-hotspot findings**: `eslint.config.js` wires in `eslint-plugin-sonarjs`'s `recommended` rule set alongside the hand-picked `STRICT_RULES` — this is SonarSource's own JS/TS analyzer packaged for ESLint, not a lookalike. Treat any `sonarjs/*` finding as a real SonarCloud issue in waiting. `STRICT_RULES` also carries a second batch of native ESLint "possible problems" rules (`no-constant-binary-expression`, `array-callback-return`, `no-promise-executor-return`, `no-implicit-coercion`, `no-multi-assign`, ... — the full list is in the file, each with a one-line reason) plus a security-footgun batch (`no-eval`, `no-new-func`, `no-script-url`, `no-extend-native`, `no-proto`, `no-caller`, ...) that sonarjs's `recommended` doesn't cover. All were clean when added; they exist to keep it that way, not because they found something to fix. `regexp/no-dupe-disjunctions` and `regexp/no-misleading-capturing-group` (from `eslint-plugin-regexp`) are cherry-picked the same way — both did find and fix real issues (a redundant `Ø|ø` alternative once `/i` already folds the case, a `min` alternative made unreachable by an earlier `m` in the same disjunction). The rest of that plugin's `recommended` set (capturing-group style, char-class-vs-`i`-flag preference) is deliberately left out — style opinions on already-reviewed, ReDoS-hardened regex code, not bug-finders. `unicorn/consistent-function-scoping` (from `eslint-plugin-unicorn`, cherry-picked the same way — its much larger `recommended` config is mostly style opinions this project doesn't share) reproduces SonarCloud's "Move function 'x' to the outer scope" finding exactly, message text included: a nested function that never touches its enclosing function's own parameters/closure variables gets flagged to hoist to module scope. Added after two such findings (`inspiration.js`'s `setLinkActive`, `setlist-view.js`'s row-scroll helper) showed up on SonarCloud first; turning the rule on surfaced ~30 more pre-existing instances across `static/script/songs/**`, all fixed in the same pass so the gate started clean, same as every other rule here. `unicorn/prefer-at` and `unicorn/prefer-code-point` were added the same way after PR #121's SonarCloud scan flagged `arr[arr.length - 1]` (prefer `arr.at(-1)`) and `str.charCodeAt(i)` (prefer `str.codePointAt(i)`) on brand-new code; `--fix` handled every hit project-wide except one non-mechanical case (see the `arr.at(-1)` gotcha note below the pattern list).
- **JS complexity**: ESLint's own `complexity` (cyclomatic) and sonarjs's `cognitive-complexity`, both gated by `--max-warnings 0`.
- **JS types**: `tsconfig.lib.json` runs TypeScript's `--checkJs` over `static/script/lib/**` only — the "pure, side-effect-free" modules (see Static assets layout below), which is also exactly the subset with no DOM API surface to fight. `static/script/songs/**` isn't covered: it's DOM orchestration through and through (`document.getElementById(...).value` etc.), and `checkJs` infers every DOM query as bare `HTMLElement`/`Element`, so checking it for real would mean adding a JSDoc type cast at nearly every query site across a dozen files — a lot of mechanical, error-prone busywork for a return that's mostly noise, not bugs. `lib/` type-checked clean on the first pass except for two known `checkJs`-inference gaps (`comping.js`+`comping.test.js`'s `tokenizeBar`, `setlist-walk.test.js`'s `walkSetlist`): both build a heterogeneous array via plain `.push()` calls with two different literal shapes, and `checkJs`'s inference doesn't cleanly discriminate the resulting union the way an explicit JSDoc `@typedef` would — those three files are in `tsconfig.lib.json`'s `exclude`, same reasoning as the sonarjs complexity override below. **`typescript` is pinned to an exact `5.9.3`** (not `^`) in package.json — `eslint-plugin-sonarjs` depends on `ts-api-utils`, which only supports `typescript >=5 <6.1.0`; installing a newer `typescript` (7.x was current at the time of writing) silently breaks `npm run lint:js` entirely (`ts-api-utils` throws `Cannot read properties of undefined (reading 'Intrinsic')` on load). If `npm run lint:js` starts throwing that, check what `typescript` resolved to first.
- **CSS correctness**: `stylelint.config.mjs`, extending `stylelint-config-recommended` — possible-error rules only (duplicate selectors/properties, empty rules, unknown/deprecated properties and values, invalid at-rules...), the same category SonarCloud's CSS analyzer covers. It deliberately does *not* extend a stylistic/naming config (`stylelint-config-standard` and its kebab-case selector rules): `assets/css/split.css`'s existing camelCase ids/classes are load-bearing (the JS references them by exact name), and blanket-reformatting a 3000+ line hand-authored stylesheet for style alone isn't a correctness win. `no-descending-specificity`, `selector-max-compound-selectors` and `selector-max-id` are deliberately left off too: retrofitting cascade order or selector shape on this file means visually re-testing a live production stylesheet this sandbox can't render — a cost with no correctness payoff, and not something SonarCloud's own CSS analyzer checks for either.
- **Duplication**: `jscpd.config.json` runs jscpd (`min-lines: 10`, `min-tokens: 50`) over `static/script`, `assets/css` and `tests`, gated at `threshold: 1` (percent duplicated lines) — tighter than SonarCloud's own default "Duplicated Lines (%)" gate of 3%, since the project sits at ~0.3% and a 1% ceiling still leaves 3x headroom while catching a regression earlier. A few small, acknowledged clones survive under that gate on purpose (test-fixture setup that's clearer written out than abstracted, e.g. `chords.test.js`'s two `parseChordScheme` fixtures) — don't chase those down reflexively; do dedupe anything that pushes the total meaningfully. (Real, non-fixture duplication *has* turned up this way before: jscpd caught `comping.test.js` carrying its own full copy of the Tonal stub `tests/helpers/stubs.js` already exported, down to an identical bug in one of the two copies.)

**This local set is a proxy, not the real thing, and it has known gaps.** PR #42 (the one that first built this lint layer) got real SonarCloud feedback once opened: 7 new-code issues that none of the above caught — `parseInt`/`parseFloat` vs `Number.parseInt`/`Number.parseFloat` (consistency rule, 3 hits), `str.match(re)` vs `re.exec(str)` for a non-global regex used for its capture groups, a closure-independent function nested one level deeper than it needed to be, a bare no-op expression statement (`grid.offsetWidth;`, written that way specifically to dodge `sonarjs/void-use` — satisfying one Sonar rule this way tripped another), and one deprecated-API call SonarCloud considers a "new" issue because the *line* changed even though the call itself (an intentional legacy fallback) predates this PR. The first four are now real ESLint rules (see `no-restricted-globals`, `no-unused-expressions` in `eslint.config.js`); the fifth got a `// NOSONAR` with a comment explaining why, right on the line. Moral: `npm run lint` passing is strong evidence, not proof — SonarCloud's actual JS rule catalog is bigger than what `eslint-plugin-sonarjs`'s `recommended` config exposes, and a PR can still fail the gate on something outside it. When that happens, check the PR's SonarCloud check / GitHub PR comment for the issue list (rule, file, line) and feed it back into this file the same way.

**Known gap: "prefer optional chain."** SonarCloud flags `a && a.b` (and similar `&&`-guard chains) as preferring `a?.b`. There's no local rule for this: `eslint-plugin-sonarjs` doesn't have one, and the only ESLint rule that does — `@typescript-eslint/eslint-plugin`'s `prefer-optional-chain` — requires full type-aware linting (`parserOptions.project` on `@typescript-eslint/parser`) to run at all, the same type-checking machinery `static/script/songs/**` is deliberately excluded from above (DOM queries all infer as bare `HTMLElement`, drowning any real signal in noise). Standing up project-wide type-aware linting just for this one rule isn't worth that cost. Until SonarCloud ships this as a plain `sonarjs/*` rule, treat it as SonarCloud-only: fix it by hand when the PR check flags it (swap the `&&` guard for `?.`), same as any other gap in this list.

A few patterns come up repeatedly and are worth avoiding by habit rather than fixing after the fact:

- **Regexes that scan for a closing delimiter** (`"[^"]*"`, `\{[^}]*\}`, `\s*literal`, `(\d+)$`, …) trip `sonarjs/super-linear-regex`: an unanchored quantifier that fails to match still costs work at *every* start position, which is quadratic on adversarial input. Prefer a plain scan — `str.indexOf(close, i)`, a manual char-class walk (see `stripDelimited`/`scanRun`/`scanNoteLetter` etc. in `static/script/lib/comping.js`), or `String#trimEnd()` — over a `delimiter...*...delimiter` regex, especially in `lib/` parsers that run over arbitrary ABC/setlist text.
- **Two optional quantifiers either side of an optional separator** (`(\d+)?(\/+)?(\d*)`) are ambiguous — when the separator is absent, both groups can claim the same run of characters, which is exactly what makes backtracking explode. Nest the second group inside the separator's: `(\d+)?(?:(\/+)(\d*))?`.
- **A `try` whose catch ignores the exception** (`catch (_e) { /* comment */ }`) only passes `sonarjs/no-ignored-exceptions` when the `try` block is a single simple statement — a comment doesn't satisfy it. If the try body is a multi-step operation, pull it into its own function so `try { return doTheThing(); } catch { return fallback; }` is the whole block.
- **A `finally`-shaped cleanup written as a trailing statement instead** (`doThing(); cleanup(); return x;`, where a throw from `doThing()` skips `cleanup()`) leaks whatever `cleanup()` was supposed to release. If the two are ever in the same function, the cleanup belongs in an actual `try { ... } finally { cleanup(); }`, not after the risky call.
- **Nested ternaries** (`a ? x : b ? y : z`, or a ternary nested in another's branch) trip `sonarjs/no-nested-conditional` — use `if`/`else if`/`else` assigning to a `let`, or extract the inner ternary to its own statement.
- **A string literal repeated 3+ times** in one file trips `sonarjs/no-duplicate-string` (threshold 5 here) — hoist it to a `const`.
- **`void expr`** trips `sonarjs/void-use`, a bare `expr;` statement with no assignment trips `no-unused-expressions`, *and* `const _x = expr;` still trips SonarCloud's own unused-variable rule (it doesn't recognize ESLint's `_`-prefix-means-intentional convention — this project hit all three in turn on the same line). For the "read a property to force a reflow" idiom, wrap the read in a tiny helper that `return`s it (see `forceReflow` in `static/script/songs/chord-table.js`) and call that as a statement — a function call, unlike a bare property read, is a normal statement no rule objects to.
- **`parseInt`/`parseFloat`/`isNaN`/`isFinite` as bare globals**: `parseInt`/`parseFloat` are banned outright by `no-restricted-globals` (`Number.parseInt`/`Number.parseFloat` are the literal same function, zero behavior change — always safe to swap). `Number.isNaN`/`Number.isFinite` are *not* drop-in for the global forms (they skip the implicit `ToNumber` coercion), so those aren't banned — check the call actually receives a number before swapping it.
- **`str.match(regex)`** where `regex` has no `/g` flag and the code wants the capture groups (not "is there a match" — that's `regex.test(str)`) trips SonarCloud's exec-preference rule — use `regex.exec(str)` instead; identical result, no flag-dependent behavior to reason about.
- **A nested function that never touches its enclosing function's parameters/closure variables** is flagged as needing to move to module scope — if it only uses its own arguments and globals, hoist it out from under the factory function it happened to get written inside. `unicorn/consistent-function-scoping` catches this locally now (see above), so `npm run lint:js` fails before this one ever reaches SonarCloud.
- **An alternation branch that's already covered by an earlier one** (`(m|min|...)` — `min` can never win, `m` already matched) or **that becomes a duplicate once a case-insensitive flag folds it** (`(Ø|ø|...)/i` — `ø` is dead once `/i` already matches it) trips `regexp/no-dupe-disjunctions`. Order alternatives longest/most-specific first, and don't spell out both cases of a letter in an already-`/i` pattern.
- **A call to a genuinely-deprecated API that's intentional** (a legacy-browser fallback with no non-deprecated equivalent, e.g. `document.execCommand("copy")` for pre-Clipboard-API browsers) — add `// NOSONAR` on that exact line with a comment explaining why there's no better option, rather than trying to restructure code that has nothing to restructure toward.
- **`arr.at(-1)` / `arr.at(-N)`** trips the browser-code `no-restricted-syntax` ban on `.at()` (see **Browser support** below) — use `arr[arr.length - N]` instead. This used to run the other way (a since-removed `unicorn/prefer-at` rule required `.at()`, on the strength of a matching SonarCloud finding) — mind the direction if you're recalling that rule from memory or from an old diff. Whichever direction, the same `NodeList` gotcha applies: `NodeList` (what `querySelectorAll` returns) has no `.at()` method despite having `forEach`/`entries`/`[Symbol.iterator]`, so indexing `someNodeList[someNodeList.length - 1]` directly is also wrong — route through the project's own `qsa()` helper ([lib/dom.js](static/script/lib/dom.js), which already wraps the result in `Array.from`) or spread it (`[...el.querySelectorAll(...)]`) first (PR #121 hit the array-autofix-on-a-NodeList version of this mistake; keep the general shape of the gotcha in mind either direction).
- **`str.charCodeAt(i)`** trips `unicorn/prefer-code-point` — use `str.codePointAt(i)` instead; identical for any index that isn't the low half of a surrogate pair (i.e. every ASCII/BMP case this codebase's regexes and note/chord parsers actually hit), and correct where `charCodeAt` silently isn't.

`static/script/lib/chords.js`, `comping.js` and `music-theory.js` carry a scoped override in `eslint.config.js` turning off `sonarjs/cognitive-complexity` and (for `comping.js`'s one literal-alternation barline tokenizer) `sonarjs/regex-complexity` — these are dense, heavily unit-tested pure parsers where splitting a single-pass loop mid-stream hurts readability more than the branch-count metric helps; don't reach for that override elsewhere without the same justification (tests as the guard rail, no simpler equivalent structure). `comping.js` (plus `comping.test.js` and `setlist-walk.test.js`) are excluded from `tsconfig.lib.json`'s type-check for the analogous reason given above.

### Browser support

The `/songs/` page (and `/agenda/`) must keep working on **Safari 12** (iOS 12), not just current browsers — found the hard way when a real visitor's iPad Air (2013 hardware, permanently capped at iOS 12.5.8, the last update Apple ever shipped for it) loaded the page to a totally inert shell: static markup rendered, nothing interactive worked, no console the visitor could see to explain why. The cause: `static/script/**` loads as one ES module graph, and it used `?.`/`??` in a dozen-plus files. Safari 12 predates both — either one is a `SyntaxError` at *parse* time, which aborts the whole graph before a single line runs, not just the file that has it. `Array/String#at` (Safari 15.4+), `String#matchAll` (Safari 13+) and `String#replaceAll` (Safari 13.1+) are the same story minus the total-blackout part — they don't exist on Safari 12 either, but only throw once actually called, so they take out whatever function reaches them rather than the whole page.

`eslint.config.js` has a browser-code-only block (`static/script/lib/**`, `static/script/songs/**`, `static/script/*.js`, excluding `*.test.js` — the Node test suite doesn't run in a browser at all, so it's unrestricted) enforcing this going forward:
- `no-restricted-syntax` bans the `ChainExpression` node (`?.`, any position in a chain) and `LogicalExpression[operator='??']` outright — there is no partial-support way to keep these, so write the guard by hand: `a && a.b` for optional chaining, `x === undefined ? fallback : x` for nullish coalescing (add an explicit `=== null` check too only when the value can genuinely be either, not just undefined — e.g. a function parameter, unlike a `Map#get`/array-index/`Array#find` result, which are undefined-only on miss).
- The same rule bans calling `.at(`, `.matchAll(` or `.replaceAll(` as a method. For `.at(-N)`, index from the end manually: `arr[arr.length - N]` (mind the `NodeList` gotcha noted just above). For `.replaceAll(regex, ...)` where `regex` already carries `/g`, swap to `.replace(regex, ...)` — identical result, since a global regex is exactly the case `replaceAll` was generalizing `replace` to. For `.matchAll(regex)`, use [`lib/regex-exec-all.js`](static/script/lib/regex-exec-all.js)'s `execAll(regex, str)`, a manual `exec()`-loop with the same "returns every match, resets the regex's own `lastIndex` first" contract `matchAll` has (safe to call twice in a row on the same shared, module-level regex, unlike a raw `exec()` loop).
- `logical-assignment-operators` (further up, in `STRICT_RULES`) is flipped from its default "always require `&&=`/`||=`/`??=`" to `"never"` (forbid them) — those operators are Safari 14+, so the rule's own default would otherwise nudge new code straight at another Safari-12 SyntaxError.

This is a real, ongoing constraint on what JS syntax/APIs any change to `static/script/**` can use, not a one-off cleanup — SonarCloud and the rest of this file's lint guidance assume a current-browser target and will happily suggest `?.`/`??`/`.at()` again; the ESLint rules above (and the two more just below) are what actually catches it before it ships. There is no build/transpile step (see the top of this file) turning modern syntax into old-Safari-safe code, so whatever's actually committed here is what runs, unmodified, on Safari 12 in this codebase — if that build-step tradeoff is ever revisited, this whole section (and its `eslint.config.js` block) would be the ones to reconsider.

**This isn't only a JS-language-syntax constraint — Web/DOM APIs matter just as much, and are easier to miss.** The first pass here only fixed `?.`/`??`/`.at()`/`matchAll`/`replaceAll` (JS language features, mechanically greppable), which got the page parsing and executing again — but `lib/dom.js`'s `clear()` helper still called `Node#replaceChildren()` (Safari 16.4+), and `lib/setlists-store.js`'s id generator still called `crypto.randomUUID()` (Safari 15.4+). Neither is a parse-time `SyntaxError`, so neither showed up in the ES2019-parser check the first pass used to verify itself — they're ordinary property lookups that only throw `TypeError: ... is not a function` once actually *called*, so the failure stayed hidden until someone exercised that exact code path on the real browser (in `clear()`'s case: the very first thing `library-tab.js`'s `render()` does, so the song list silently stayed empty — with no error visible anywhere, since it throws inside an async XHR callback no synchronous `try`/`catch` around `app.js`'s `start()` phases can catch). `no-restricted-syntax` now also bans `.replaceChildren(` (use `clear()`, then `.append(...)` if you need to insert new children too) and `crypto.randomUUID()` (use `Date.now().toString(36) + Math.random().toString(36).slice(2, 10)` for a non-cryptographic local id, same as `lib/setlists-store.js`'s `generateId`). The lesson for next time: a Safari-12 audit has to check *both* categories — language syntax (parse-time, catchable by a script that parses every file with an old-ecmaVersion parser) and Web/DOM API surface (runtime, not parse-checkable — has to be grepped for by name, method by method, against what Safari 12 actually shipped).

**Known, deliberately unfixed gap: Pointer Events.** `setlist-view.js`'s row drag-to-reorder and `inspiration.js`'s panel resize/A-B-marker drag all use the Pointer Events API (`pointerdown`/`pointermove`/`setPointerCapture`/...), which is Safari 13+ — Safari 12 has no such event type at all. This doesn't crash anything: an `addEventListener` for an event type the browser doesn't recognize is simply inert, so the handler (and whatever Safari-12-missing method it calls inside) never runs. The practical effect is narrower than a crash but still real — those specific drag interactions just don't respond on Safari 12, with no feedback that anything's wrong. Left as-is for now (a real fix means a parallel mouse/touch-event fallback path for every such drag site, a bigger and more UX-sensitive change than swapping one method call) — revisit if it turns out to matter in practice.

## Architecture

**Red Jackets Jazzband** website: a Hugo static site with multi-language support (English, Dutch, German, French) and interactive music features powered by vanilla JavaScript.

### Hugo setup
- Config: [config.toml](config.toml) — base URL, languages (en/nl/de/fr, each with its own `locale` for `<html lang>`/hreflang/sitemap), theme params, privacy settings
- Theme: `Split` by escalate, managed via [dfetch](dfetch.yaml) (not a git submodule) into `themes/split/`
- Content: Markdown files with TOML frontmatter, language-suffixed filenames (e.g. `band.en.md`, `band.nl.md`, `band.fr.md`)
- Deployed to a separate GitHub Pages repo (`red-jackets-jazzband.github.io`) via GitHub Actions on push to `master`

### Public content pages
All of `/`, `/agenda/`, `/band/`, `/in-action/` (each with `/nl/…` + `/de/…` + `/fr/…` variants from language-suffixed content files) render through the Split theme's one split layout: fixed image column left (`quedlinburg_back_name.jpg`, `center top`), scrolling content column right on `#1b1b1b`, Montserrat headings + Lora body, gold `#e29d0f`, magenta `#CA486d` on hover. The page markdown is just the body that drops into `.split-bio`; the `tagline` frontmatter is the big heading.

### Music interactive pages
`/songs/` ([content/songs.md](content/songs.md)) is one interactive shell — a library sidebar with a **Library / Setlists** tab switcher, plus a single-song sheet. It loads one entry point, [static/script/songs-page.js](static/script/songs-page.js), which starts `songs/app.js`. Which tab starts active is set by `data-default-tab` on `.rj-songs-layout` (defaults to `library`). The old `/setlists/` and `/songbook/` routes are now Hugo aliases redirecting to `/songs/`.

**Module layout** ([static/script/songs/](static/script/songs/)): `app.js` is the composition root — it builds one shared `ctx` (mutable state + cross-module methods) and instantiates every module against it. Modules reach each other only through `ctx`, never by importing one another. Key modules: `sheet` (the render pipeline, live + booklet), `chord-table`, `sheet-decorations` (part-marker boxes + comping notehead colours), `audio-player` (SynthController lifecycle, transport, highlight, seek, tempo), `sheet-controls` (Key/Tempo steppers, transport buttons, advanced toggle, print link, Spacebar play/pause), `selects` (instrument + comping dropdowns), `inspiration` (YouTube/Spotify PiP, YouTube's own LoopTube toolbar), `irealpro-link`, `library-tab`, `tour` + `tour-actions` (the guided first-time tour — see below), `swipe-nav` (mobile left/right swipe across `#rjSheet` to step to the prev/next song — through an open setlist's songs on the Setlists tab, or the sidebar's rendered library list on the Library tab; the touch counterpart of the Up/Down arrow keys, gesture maths in `lib/swipe.js`), and `setlist-{data,home,modal,view,print}`. `read-file.js` is the shared XHR helper. Pure logic lives in `static/script/lib/` (see below).

**Library tab** ([songs/library-tab.js](static/script/songs/library-tab.js), rendering via [songs/sheet.js](static/script/songs/sheet.js)):
- Loads ABC notation files from [static/songs/](static/songs/) (146+ songs) via XHR, index at `static/songs/index_of_songs.txt`
- Search-first list with an A-Z scroll rail; picking a song renders it into the shared sheet
- Sheet header (left to right): the **Instrument** dropdown, **Key** and **Tempo** steppers, **Play** (with Stop and Mixer; **Spacebar** toggles play/pause whenever a sheet is open and the focus isn't in a text field or on a button), a contextual **Inspiration** button, and an action cluster of icon-only buttons — **Print**, **Export MP3** and **iRealPro** (the latter appended at runtime for any tune that has chords). There is no in-page export panel: a single chart prints via **Print** (save-as-PDF for a PDF), and a multi-song print is one of the Setlists tab's three "Print …" buttons. Instrument lives here (not the sidebar) since it's the same button bar as Key/Tempo/Play; the row wraps onto a second line when it doesn't all fit, same as the mobile layout. Key's caption reads "semitones" and Tempo's reads real bpm (seeded from the tune's own `Q:` field), not an abstract percentage
- **Repeat stepper** (`#repeatStepper`, wired in `sheet-controls.js`, state and playback logic in `audio-player.js`): a 1-20 count of how many times in a row a song plays, for practicing on a loop. It's not something you reach for mid-song like Key/Tempo, so it lives behind the **More controls** drawer alongside the comping dropdown (`.sheet-adv-row`) rather than the always-visible toolbar, and is persisted like the other sticky sheet prefs (`PREF_KEYS.repeatCount`). When a tune finishes naturally with playthroughs still remaining, `audio-player.js`'s `tryRepeat()` seeks the same `SynthController` back to the top and plays again — but only the very first playthrough includes a pickup/anacrusis: `buildTimingMap` records `state.firstBarMs` (the offset of the tune's first full/"double" bar, measureIdx 1), and every repeat pass but the first restarts there instead of position 0 (`repeatRestartFraction`), so the lead-in note(s) aren't replayed every time round. The Repeat stepper's own label doubles as a live progress readout ("2 of 4") while a multi-repeat loop is actually playing. The metronome click (when enabled) ticks straight through a repeat restart uninterrupted — it's never told playback stopped, since a loop restart isn't a real stop/start — and simply resyncs itself at the next real bar line the same way it already does for ordinary tempo/measure drift.
- **Export MP3** (`#exportMp3Btn`, driven by `songs/mp3-export.js`; the byte-pushing in `lib/mp3-encode.js`): renders the sheet's current audio — instrument, key, tempo, comping, every Mixer channel's mute/volume/voice, and the Repeat stepper's own count, exactly as heard through Play — to a downloaded `.mp3` file, named after the tune's own `.abc` filename. It doesn't touch the live playback `SynthController`; audio-player.js's `buildExportOptions()` hands over the same visualObj and synth params (see `synthParams()`), plus `repeatCount` and `restartFraction` (the same pickup-skip fraction `tryRepeat()` seeks to — see the Repeat stepper bullet above), through a throwaway, offline `ABCJS.synth.CreateSynth()` instead, since that's the one ABCjs object that exposes its rendered `AudioBuffer`s (`.audioBuffers` after `.prime()`) rather than just playing them. `CreateSynth` has no `setWarp`; its only tempo knob is `millisecondsPerMeasure`, so the Tempo stepper's warp percentage is applied to it the same way `setWarp` applies it internally (scale the tune's native ms/measure by `100 / warp%`). `CreateSynth` only ever renders one playthrough, so `lib/mp3-encode.js`'s `encodeMp3` takes `repeatCount`/`restartFraction` as options and loops the render into the encoder itself — the first pass in full, every later one starting `restartFraction` of the way through (a plain 0..1 fraction of the tune's own duration, so it applies unchanged regardless of this render's own tempo) — the export-side mirror of the live practice loop. It's deliberately *not* a step of "build a second, `repeatCount`-times-longer buffer, then encode that": the render is resampled/converted to PCM once, and that one array (or, past the pickup, a zero-copy `subarray` view of it) is fed into the *same* streaming lamejs encoder session once per repeat — at 20 repeats of a several-minute tune, concatenating first would mean allocating a buffer sized for the entire looped duration up front (over a gigabyte for a long stereo tune), which can freeze or crash the tab. `encodeMp3` first resamples the rendered PCM up to a fixed 44.1kHz (ABCjs's offline synth actually renders at its own undocumented rate — empirically 32kHz — with no option to configure it), duplicates a mono render across both channels so the output is always stereo, converts to 16-bit samples, and feeds them through the vendored `lamejs` MP3 encoder (`static/script/lamejs-1.2.1-min.js`, loaded as a classic script alongside ABCjs/Tonal, global `lamejs.Mp3Encoder`) at a fixed 192kbps — a reference export for musicians, not a mastering deliverable, but at a standard rate/bitrate rather than whatever the synth happens to natively produce. It's unit-tested against a fake `lamejs` (`tests/helpers/stubs.js`'s `createLamejsStub`/`withLamejs`) rather than the real encoder, the same way ABCJS/Tonal are faked elsewhere, so the suite stays fast and jsdom-free (no real `AudioContext` either). The button is enabled/disabled alongside Play/Stop/Mixer (same `setButtonsDisabled` in audio-player.js), since export needs the same audio-capable tune; a spinner replaces its icon while the offline render is in flight.
- **Full screen** (`#sheetFullscreenBtn`, a regular standalone `.sheet-icon-btn` right after the `#sheetActions` cluster (Print/Export MP3/iRealPro) rather than folded into that pill — full screen isn't a tune-specific export action like those three — driven by `songs/fullscreen.js`): toggles `body.rj-sheet-fullscreen`, which pins the whole `.rj-songs-layout` over the viewport (split.css) and hides the masthead photo and the page's own title/language switcher (`.split-image`, `.split-intro`). It gets the same `.active` gold-fill treatment as the Mixer button while the mode is on, rather than its own bespoke styling. Deliberately CSS-only, never the real Fullscreen API (`Element.requestFullscreen()`) — mobile browsers suspend pinch-zoom for as long as a genuine fullscreen element is active, which would defeat the point of a mode built for reading a dense chart up close on a phone; with no `requestFullscreen()` call, the page's own native pinch-zoom keeps working right through it. Portrait has no room to spare for the library/setlist sidebar next to a lead sheet, so the sheet alone fills the screen; landscape has the width of the ordinary desktop split to spare, so the sidebar stays visible on the left (an `@media (orientation: landscape)` override) — letting you keep switching songs without leaving full screen, confirmed to persist correctly across a sidebar song pick. `#sheetmenu` is pinned `position: sticky` at the top of `#rjSheet`'s own scroll box while active, so the whole toolbar — including this button — stays in reach as a long chart scrolls underneath, with no separate pinning needed for the button itself. Also requests a Screen Wake Lock (`navigator.wakeLock`, best-effort — not every browser implements it) for as long as full screen stays on, re-requested on `visibilitychange` since the spec releases it automatically the moment a tab is backgrounded (e.g. a phone screen lock/unlock).
- **Mixer** (`#mixerBtn` → `#mixerPanel`, driven by `songs/mixer.js`; pure text maths in `lib/audio-mix.js`): replaced the old boolean "mute melody" button. Two fixed channels, **Bass** and **Chords** (ABCjs's own auto-generated accompaniment), each a mute button, a real 0-100 volume fader and a **Voice** picker (a curated GM-instrument `<select>`, `lib/gm-voices.js`; grouped Keys/Guitars/Bass/Brass/Reeds, built the same way `selects.js` builds the Instrument/Comping dropdowns), sticky across songs via `localStorage` (`PREF_KEYS.mixer*`). The panel is a `position: fixed` popover anchored under the button on desktop (positioned from the button's own rect, since #rj-sheet clips overflow) and docks as a full-width bottom sheet with a dimming backdrop under the 1024px breakpoint (CSS `!important` overrides the JS-set coordinates there).
  Above Bass/Chords sits the tune's own **voice list** — the one generalisation the whole panel is built on: a tune is always *N* voices (its own melody line for an ordinary tune, or however many named staves a chart like a Rebirth Brass Band tune's Trumpet + Sousaphone declares), plus **Comping** appended as voice *N+1* whenever its pattern picker is on. There's no separate "Melody channel" or "Comping channel" any more — `lib/audio-mix.js`'s `resolveMixerVoices(rawVoices, compingActive)` turns `parseVoiceList`'s raw scan of the tune's own `V:` declarations (name="..." and all — this reads only the source text, never the comping-generated split) into that one resolved list, naming each voice from its own `name="..."` when the ABC has one, else `"Melody"` (a lone unnamed voice) / `"Melody 1"`, `"Melody 2"`, ... (two or more unnamed voices) / always literally `"Comping"` for the appended one, never folded into the Melody-numbering scheme. `sheet.js` hands the resolved list to `songs/mixer.js`'s `syncVoices()` on every render, which builds one dynamic strip per voice (`#mixerVoicesSection`/`#mixerVoicesList`, replacing content/songs.md's old fixed Melody/Comping markup) and persists each by a slug of its own resolved name (`rj.mixerVoice.<slug>.muted`/`.program`) rather than by song + numeric id — every "Sousaphone" part across every song on the site, or every song's own "Comping" voice, shares one sticky Mute/Voice choice. Comping's appended id is always "whatever the next free voice slot is" (`lib/comping.js`'s `nextVoiceId`, shared with `resolveMixerVoices` so both agree) — `buildCompingTune` layers Comping onto a chart that already declares more than one voice of its own the same way it does for an ordinary single-voice tune: the tune's own voices and layout are left untouched, and Comping is appended as one more voice past however many the chart already has (see its own doc comment), so a Trumpet+Sousaphone-style chart gets a real, generator-backed Comping strip in the Mixer too, not just a single-voice tune.
  Every voice channel gets the same *kind* of control now — **Bass**/**Chords** and every resolved voice all get real, working Mute, Voice **and Volume** — though the two groups reach a working volume through different text directives, because ABCjs's live web-audio synth turned out not to honor everything its own text-directive parser accepts equally — confirmed empirically in a real browser, not just from source-reading. See `lib/audio-mix.js`'s doc comment for the mechanism split; the short version:
  - **Bass**/**Chords** are ABCjs's own auto-generated accompaniment (the classic abc2midi `%%MIDI gchord`/`bassprog`/`chordprog`/`bassvol`/`chordvol` engine — see https://examples.abcjs.net/accompaniment), driven entirely by the tune's existing chord symbols, with **no notation drawn for it** — a different mechanism from, and layered independently on top of, the notated Comping voice. `sheet.js`'s `engrave()` calls `injectMixerAudio` to stamp those five directives into the tune header whenever `ctx.state.hasChords` (regardless of whether Comping is on) — these ARE read by the live synth, not just ABCjs's separate "export as .mid file" path, which is what makes them real. Muted by default (`songs/mixer.js`'s `DEFAULT_MUTED`) so no song suddenly grows a new backing band the first time this ships. Gated on `hasChords`; a gated channel with nothing to mix hides its entire strip (swatch, label, fader, mute, Voice, readout) outright via `.mixer-strip.is-inactive` rather than staying clickable with no audible effect. The Pattern picker's gate (also `hasChords`) hides the same way.
  - Every resolved voice is a regular ABC voice (Melody, a chart's own named staves, or the generated Comping voice, per `buildCompingTune`'s `V:1`/`V:2` contract when it's active). A generic `%%MIDI vol` on an ordinary voice was tried first, exactly mirroring the proven Bass/Chords approach — and does nothing worth building on: reading ABCjs's own flattener source shows `%%MIDI vol` only overrides the *single next note*, then reverts, so a one-off line is barely audible and can't hold a fader position. `%%MIDI beat ⟨b1⟩ ⟨b2⟩ ⟨b3⟩ ⟨mod⟩` (abc2midi's directive for a bar's first/other-strong/weak note volumes) turned out to be the real lever instead: ABCjs's flattener keeps those three numbers as *persistent* per-voice state rather than a one-shot, so setting all three to the same value scaled by the fader (`lib/audio-mix.js`'s `beatStressLine`/`percentToBeatStress`, scaling ABCjs's own defaults 105/95/85 down together so a fader at 100% sounds exactly as it always did) gives a real, working volume — confirmed the same way as `%%MIDI program` below: empirically, by rendering a voice offline through `ABCJS.synth.CreateSynth` (the same engine `SynthController` primes for live playback) and measuring that the output buffer's amplitude scales linearly with the value, not just from reading the source. One real gotcha the same test surfaced: those three stress numbers are shared, tune-wide state in ABCjs's flattener that resets once per tune but *not* per voice, so a voice with no `%%MIDI beat` line of its own silently inherits whatever level the previous voice's stream left behind rather than ABCjs's own default — `injectMixerAudio` therefore always stamps a `%%MIDI beat` line for every resolved voice, including ones left at 100%, never only the ones a user actually moved. This line is stamped right alongside `%%MIDI program` — both go through the same one scoping pass (`injectPerVoiceLines`, matched the same way `parseVoiceList` finds a voice's own **first declaration line**, wherever it falls relative to `K:`) for their Voice + Volume; the one tune shape with no such line to scope to at all (an ordinary single-voice tune, no `V:` declaration, Comping off — the vast majority of songs here) falls back to one tune-wide `%%MIDI program` + `%%MIDI beat` pair before `K:`. Mute goes through a *third*, different mechanism, since it isn't a text directive here at all — `audio-player.js`'s `synthParams()` calls `lib/audio-mix.js`'s `computeVoicesOff(voices)`, which sets SynthController's own `voicesOff` option (a single voice mutes as `true` — the one form already proven in a real browser from before per-voice channels existed — two or more voices mute independently by index, unambiguous, no text-directive guessing). Their Voice picker's stored program is `null` until explicitly overridden, same `null`-sentinel convention as Bass/Chords, so an untouched picker changes nothing audible and a future default change reaches everyone who's never touched it — but the `<select>` itself never shows a "Default" placeholder: left un-overridden, it's pre-selected on `lib/gm-voices.js`'s `guessGmProgram` (matching the voice's own resolved name against a curated set of keyword hints — "Sousaphone"/"Tuba" → GM Tuba, "Trumpet" → GM Trumpet, ... — falling back to Trumpet, today's one hardcoded program before the Mixer existed, for an unrecognised or generic "Melody"/"Comping" name), so it always reads as whichever real instrument is actually sounding (`songs/mixer.js`'s `resolveEffectiveProgram`).
  Bass/Chords' fader maps its 0-100 percent to ABCjs's 0-127 MIDI volume on a cubic curve, not linear (`lib/audio-mix.js`'s `percentToMidiVolume`, `VOLUME_CURVE_EXPONENT`) — most of the slider's travel goes to the quiet-to-comfortable range for finer control there, the same taper a real mixing console fader uses, rather than spreading evenly up to "as loud as it gets". A resolved voice's own fader reuses the same cubic taper (`percentToBeatStress` scales ABCjs's three default stress values by the same curve) rather than one flat number, so a voice's natural downbeat/upbeat accent survives at any fader position instead of flattening out.
  **Deferred**: the Comping voice's three chord tones (root/3rd/5th, the black/gold/magenta noteheads) are not separately mixable even once Comping's own mute/volume is real — `buildCompingTune` emits them as simultaneous notes inside *one* chorded ABC voice (one stem per hit, by design), so there's no per-note audio hook to isolate them, and ABCjs's own gchord/bass split only goes two ways — bass vs. one strummed chord-tone group — not three individually addressable tones either. Doing this for real means rewriting the comping generator to emit root/3rd/5th as three separate monophonic ABC voices — a change to the voice-leading/chord-stacking engine and the printed notation layout (and booklet rendering), not just the mixer.
- Renders notation using [ABCjs](https://paulrosen.github.io/abcjs/) (library bundled in `static/script/`)
- Transposition: real-time for Concert, Alto Sax (+9), Bb Clarinet/Trumpet (+2), Tenor Sax (+2), Trombone (bass clef), Sousaphone (bass clef). The Key stepper's semitone offset transposes **both** the printed notation (ABCJS `visualTranspose`) and the audio (ABCJS `midiTranspose`, set independently — `visualTranspose` alone is notation-only and never reaches the synth); the instrument's own offset is folded into `visualTranspose` only, so playback always sounds the same concert pitch no matter which instrument's part is on screen
- Chord analysis: parses chords from ABC, converts to Roman numeral notation using [Tonal.js](https://github.com/tonaljs/tonal) (`static/script/tonal.min.js`)
- Audio playback via ABCjs SynthController with FatBoy soundfont (trumpet); the Tempo stepper holds a real bpm value, converted to ABCjs's "warp" percentage (`bpm / nativeQpm * 100`) and applied via `SynthController.setWarp`, which re-primes the MIDI buffer and resumes playback itself. `setTune`'s `qpm` option does **not** work — SynthController's `go()` drives playback purely from the tune's `millisecondsPerMeasure` and `warp`. `setWarp` internally writes to a `.abcjs-midi-tempo` DOM element, so the player is loaded with `displayWarp: true` (the `#abc-player-container` is `display:none`, so nothing shows)
- iRealPro URL generation for mobile musicians
- Inspiration: when a song's ABC has one or more `F:` fields, a per-song button opens a docked, draggable picture-in-picture panel (`#inspirationPanel`, driven by `songs/inspiration.js`) — it keeps playing across song navigation until explicitly closed, instead of leaving the page. A tune's F: links are classified by host (`static/script/lib/inspiration-links.js`); the panel embeds up to three of them — a YouTube link (privacy-enhanced player, URL parsing/embed-building in `static/script/lib/youtube.js`) with the full LoopTube toolbar described below, and/or a Spotify link (`static/script/lib/spotify.js`) and/or a SoundCloud link (`static/script/lib/soundcloud.js`) as deliberately plain embeds — each widget draws its own play/pause/seek bar, a logged-out Spotify listener only ever gets a preview anyway, and neither has an equivalent of YouTube's freely streamable, scriptable playback, so there's no LoopTube-style toolbar built for either. SoundCloud's embed is built by handing its own player widget (`w.soundcloud.com/player`) the original page URL directly (it resolves the track/playlist server-side) rather than extracting an id the way Spotify's embed does. Any other F: link (SecondHandSongs, ...) stays a plain "open in a new tab" icon button next to the Inspiration button (`songs/inspiration-links.js`) rather than an embed. When a tune has more than one of the three, a small tab switcher in the panel header (`#inspirationTabs`, hidden unless it would have fewer than two tabs to show) picks which is shown; only one plays at a time — switching tabs pauses the YouTube player or clears whichever iframe's `src` is being left — and switching back to a still-loaded YouTube video resumes rather than restarting it. The panel is resizable: drag its **left edge** (`#inspirationResizeHandle`, `initResize` — right edge stays put, held by CSS `right` when corner-anchored or by rewriting `left` once dragged) for any width between `MIN_PANEL_WIDTH` (240) and the viewport, or click the header **Resize panel** button (`#inspirationSizeBtn`) to jump to the next of `PANEL_WIDTHS` (320/420/540/680) wider than the current width, wrapping round. The video and whole panel are width-driven, so everything scales together. The chosen width is persisted in `localStorage` as `rj.inspirationWidth` (`PREF_KEYS.inspirationWidth`) and the panel is re-clamped into view if it had already been dragged. The panel has a LoopTube toolbar under the video, laid out top to bottom: an **overview strip** (always visible, not just once zoomed — its window simply spans the whole strip at 1x), the zoomed **timeline** itself, then a controls row of three independent button groups so they can wrap independently and Speed still fits on the same line as the rest at the panel's default width — a **Play/Repeat** group (play/pause, the endless-loop toggle), a **Speed** −/+ stepper walking YouTube's playback rates for slow practice, and a **Marker** group (**A**/**B**/Clear). A loop toggle repeats the A–B phrase endlessly (an ~80 ms poll that `seekTo`s back to A just before B — YouTube can't loop a sub-range natively, and setting **B** with a valid A already placed auto-enables this toggle rather than needing a separate third click).

Zoom lives on the overview strip itself rather than as a separate stepper: its own −/+ buttons flank it directly (`ZOOM_LEVELS` 1×-32×, `lib/looptube.js`'s `computeZoomWindow`), narrowing the timeline to a window centered on the current playhead so dragging A/B is far more precise than at the full clip's native pixels-per-second — there's no real audio waveform to render here (YouTube's IFrame API exposes playback control only, never the raw audio stream), so this is the actual lever available for precision. The overview strip is also a minimap: its highlighted window shows where the zoomed view sits within the whole clip (A/B echoed as ticks so they stay visible even zoomed away from them), and it's directly manipulable the way a video editor's minimap is — drag the window body to pan, drag either edge to resize (snapping to the nearest `ZOOM_LEVELS` entry via `nearestZoomLevel`, so dragging and the +/- buttons always agree on the same reachable widths), or click its background to jump the window there. Dragging a handle on the *zoomed timeline* within `EDGE_PAN_THRESHOLD` of its edge auto-scrolls the window (`panZoomWindow`) rather than trapping the handle at the visible boundary — a separate mechanism from the overview strip's own edge-resize. This needs the YouTube **IFrame Player API** (`enablejsapi=1` embed + `youtube.com/iframe_api` loaded lazily on first open + a `YT.Player` wrapping the iframe); the pure loop-range/zoom/rate/clock math is in `static/script/lib/looptube.js`

**Setlists tab** ([static/script/songs/setlist-*.js](static/script/songs/)):
- Band setlists are small markdown files in [static/setlists/](static/setlists/) (indexed by `index_of_setlists.txt`), read-only, parsed/serialized by [lib/setlist-format.js](static/script/lib/setlist-format.js) — deliberately leaning on standard markdown constructs (a heading, a link list, a blockquote) over inventing project-specific syntax, so the raw `.txt` reads (and even roughly renders) as a normal markdown document. The first `# <text>` line (a single `#`) is the setlist's title; any free-text line(s) before the first `##` heading or song line are its `desc` — paragraphs kept apart by blank lines, rendered as a print-only booklet cover page (real `\n`s survive as line/paragraph breaks via `white-space: pre-line`, not squashed to one line). A `## <label>` line (or bare `##`) splits the list into sets — Set 1 before the first one, Set 2 after it, etc. — shown as "Set N" headings on screen and in the printed booklet, with song numbers restarting each set. A song is a markdown link list item — `- [<title>](/songs/<file>.abc)`, optionally `?key=<value>` for a per-song override (a signed semitone integer or a target key name, e.g. `?key=Bb`), resolving to a signed semitone transposition via `setlistTransposeSteps` ([music-theory.js](static/script/lib/music-theory.js)): a bare signed integer is taken literally, anything else is a key name diffed against the tune's own `K:`; `formatSetlistKeyLabel` turns it back into a badge (`+2` / `−3`, or the key name). The link's path is the song's own real, fetchable URL (the same one `ctx.readFile` reads to open it); its text is cosmetic — filled in with the song's current title purely so the raw file reads well on its own (`serializeSetlistFile`'s `songName` resolver; `humanizeSongFile` when none is given, e.g. a song missing from the library index), and discarded on parse, since the app always resolves the display name live from its own song index instead of trusting it. One or more `> <text>` lines directly under a song's list item (indented to nest under it, though reading only checks for the `> ` prefix, not the indentation depth) attach as that song's **note** — a printed-setlist-only aside (e.g. who takes the solo), never shown on the song's own interactive sheet; multi-line (a bare `>` is a blank line inside it), editable per-song in an open personal setlist via click-to-edit (`setlist-view.js`'s `noteBlock`, same in-place pattern as the title rename), read-only for a band setlist. The parser still reads (but never writes) two earlier syntaxes: this format's own first cut, a bare `<file>.abc,<key>` song line with no markdown link, and before that, single-line `#`-prefixed comments — `# name,<Display Name>`, `# desc,<text>`, `# break` / `# break,<label>` — so a `.txt` exported before either change still imports cleanly.
- Creating a personal setlist: the Yours shelf ends with a single dashed **"New setlist"** button that opens a small centred modal (`#setlistModal`, markup in [content/songs.md](content/songs.md), wired by [songs/setlist-modal.js](static/script/songs/setlist-modal.js)). The modal takes a name and one of three starting points — **Empty**, **Remix a setlist** (a `<select>` of every band + personal setlist, cloned via `copyBandSetlistToPersonal`), **Upload a .txt** (a file input, parsed with `parseSetlistFile`) — then creates the (always personal, always editable) setlist and opens it straight in the sheet. Backdrop click or Escape closes it.
- Growing a personal setlist happens in a labelled **"Add to setlist"** block at the **foot of the open setlist's song list** (`buildAddSongRow`, inside the scroll area, not a toolbar), framed with a hairline rule and content at the song rows' 4px inset. Everything in it sits on a shared grid: a 34px icon gutter (search magnifier, each result's `+`, the break button's `+`) and a text column at 34px; every slot 36/34px tall, 7px radius. It holds a search-to-add field (`#setlistAddSongSearch`) whose matches open in normal flow below it as `.rj-library-add-song-result` rows — the Up/Down arrows walk a `.is-active` highlight through the results (wrapping, `moveAddSongActive`), and picking a match (click/tap, or Enter on the highlighted row / a lone match) adds the song, then clears the field but keeps it focused (`addSongByFile` / `submitAddSong` reset `addSongQuery`, `focusAddSongAfterRender` re-focuses on re-render) so you can type the next title straight away — and, as a peer slot below, **"Add a set break"** (`.rj-library-add-break`, a button not a field: transparent fill, gold on hover), which appends a divider whose label is editable inline. Breaks drag/delete like song rows and survive `.txt` export/import as `##` headings. Divider items live in the same `songs` array as `{ divider: "<label>" }` (helper `isSetlistDivider` in [setlist-format.js](static/script/lib/setlist-format.js))
- Personal setlists are stored in the browser's `localStorage` (`rj.setlists.v1`), fully editable, and portable between devices only via manual `.txt` export/import — never synced to the server:
  - **Rename**: the name shows as a plain heading; a double-click on it or the pencil beside it swaps in an edit field ([songs/setlist-view.js](static/script/songs/setlist-view.js) `initRename`). Export (`.txt` download) and delete are icon buttons on that same title row
  - **Reorder**: a per-row drag handle (`.setlist-drag-handle`, a `<button>`) — pointer-events drag only, so it works on touch (`beginRowDrag`/`onRowDragMove`/`endRowDrag`); Delete/Backspace on the focused handle removes the row (`removeRow`, the keyboard peer of each row's `.setlist-song-remove` `×` button). The handle deliberately does **not** claim the arrow keys for itself — `ownsArrowKeys` in [songs/setlist-view.js](static/script/songs/setlist-view.js) only treats form fields/`contentEditable` as arrow-key-owning, so Up/Down on a focused handle falls through to the same global step-to-next/prev-song navigation (`initArrowNav`/`stepSong`) as everywhere else in an open setlist, instead of nudging the row — reordering by keyboard alone isn't supported, only by drag. The drag relocates the row among its siblings live and renumbers as it goes (`renumberOpenSetlist`); on drop it reads the rows' `data-setlist-index` back in DOM order and persists the permutation via `setPersonalSetlistOrder(storage, id, order)`. Song and divider rows both carry `data-setlist-index` and map 1:1 to the `songs` array — `removeRow` reads that attribute live off the DOM row (not a captured index) so it stays correct after a drag
  - **Per-song transpose**: a semitone number field (`.setlist-song-semitones`), stored as the song link's `?key=` override, a signed integer. A legacy key-name override still transposes correctly but shows blank in the number field until a number is set. While a personal setlist's song is open in the sheet, nudging the **Key** stepper writes the new semitone offset straight back into that setlist row (same store/encoding; a `#transpose` `input` listener in [songs/setlist-view.js](static/script/songs/setlist-view.js)), replacing any legacy key-name override with the number
- Opening a setlist swaps the sidebar's list to its songs, in order; clicking one opens it in the **same** interactive sheet a Library song opens in (pre-seeded with the setlist's transposition), not a separate flattened view
- An open setlist has three print buttons, all feeding the one print-only hidden container (`#setlistPrintBooklet`) and all going through `setlistPrint.print(mode)` ([songs/setlist-print.js](static/script/songs/setlist-print.js)), which toggles `body.export-booklet-mode` (hides `#rjSheet` for the print) plus a `body.export-mode-<mode>` class, then calls `window.print()`:
  - **Print setlist** (`setlist`) — just a big numbered stage list of song titles (`.setlist-stage-list`, no song files fetched), numbered per set
  - **Print chordbook** (`chordbook`) — every song's title + chord grid; the exact same stacked DOM as the songbook, with `.notation` hidden in CSS
  - **Print songbook** (`songbook`) — the old "stack every song's title+chords+staff" booklet; each song is a `.setlist-booklet-song` block
  - The booklet is built in the background as soon as a setlist opens, through the same `sheet.js` `engrave()` as the live sheet (`isBooklet: true`). A booklet render must **never** write live-sheet state — `currentSongText`, `compingActive`, `audio.chordOffset`/`transposeSemitones` (`recordLiveText`/`recordLiveTune` early-return for it) — because `rerender()` re-engraves `currentSongText`: before this guard, toggling the More-controls drawer, comping or the instrument with a setlist open swapped the last booklet song onto the live sheet.

**Deep links** (URL hash, parsed/built in [lib/song-hash.js](static/script/lib/song-hash.js), driven from `app.js` `bootstrap()` / `ctx.syncHash()`): `#s=<song-slug>` opens that lead sheet (Library tab); `#sl=<setlist-id>` opens a setlist — a band one by file basename, or a personal one by its localStorage id — and `#sl=…&s=…` opens that song at its position in the list. The hash is kept in sync as you navigate (a plain reload/URL-copy lands back in the same place; `a`/`b` are normalised away). The Inspiration panel's **copy-link** button (`#inspirationShareBtn` → `ctx.shareUrl`) adds `a=`/`b=` (loop-marker seconds) and `i=1`; opening such a link (`inspiration.applyShareState`, consumed by the next `updateLink`) opens the video with the A–B loop already set.

**Guided tour** ([songs/tour.js](static/script/songs/tour.js) = overlay + step state machine + keyboard, [songs/tour-actions.js](static/script/songs/tour-actions.js) = the page-driving "hands", pure logic in [lib/tour-content.js](static/script/lib/tour-content.js) + [lib/tour-layout.js](static/script/lib/tour-layout.js)): a spotlight walkthrough for first-time visitors — dims the page, cuts a hole around the *real* control each step is about and explains it, in six chapters (Basics · Transpose and export · Listen and practise · The mixer · Setlists and printing · Comping). It only ever starts from the **?** button (`#tourBtn`, in the sidebar's tab row, `hidden` until the copy has loaded) — deliberately no unprompted first-visit offer. `app.js` calls `ctx.tour.init()` last, after `bootstrap()`.
- **The copy is markdown, in four languages**: `static/tour/tour.{en,nl,de,fr}.md`, fetched at runtime with `read-file.js` (under `static/`, not `content/`, so Hugo doesn't publish them as pages). Format (see the header comment of `lib/tour-content.js`): a `# ui` section of `key: value` UI strings, then `# chapter-id: Title` (optionally followed by a `setup:` line every step inherits) and `## step-id: Title` blocks; directly under a step heading, `target:` (comma-separated CSS selector fallbacks — the first one actually on screen wins), `setup:` (comma-separated action names) and `interactive: true`; then the body (paragraphs, `- ` bullets, inline `**bold**`/`*italic*`/`` `code` ``, rendered to DOM nodes, never `innerHTML`). **English is canonical for structure**: `target`/`setup`/`interactive` live only in `tour.en.md`; `nl`/`de`/`fr` repeat just ids + titles + bodies + the `ui` block in the same order, and `mergeTourLang` overlays them (keyed `chapter/step`, since step ids like `open`/`print` repeat across chapters; anything a translation lacks falls back to English). `tests/tour-content.test.js` reads the real files and fails on a missing translation, reordered ids, a `setup:` name that isn't a real action, a selector that isn't valid, or a target that's no longer in `content/songs.md` (or in the runtime-created list at the top of that test — keep it in sync when a tour target is created by JS). Language: saved choice (`rj.tourLang`) → URL prefix `/nl/`/`/de/`/`/fr/` (the site's convention, though `/songs/` itself is English-only) → `navigator.languages` → `en`; an EN·NL·DE·FR switcher in the card re-renders the step in place. The page's own labels stay English, so the copy quotes them verbatim inside translated sentences.
- **`setup:` actions** (`TOUR_ACTION_NAMES`: `showLibrary`, `showSetlists`, `openDemoSong`, `openDemoSetlist`, `openDrawer`, `openMixer`, `openInspiration`, `compingOn`) move the real page into the state a step needs, through `ctx` or a real click — they're idempotent ("make it so"), because a step's setup re-runs on every visit in either direction. Panels are *only* open because the current step names them: `apply()` closes the mixer/Inspiration panel/More-controls drawer first unless the step asks for them, so Back and chapter jumps leave nothing dangling. The demo is `bourbon_street_parade.abc` (chords + YouTube/Spotify `F:` links, full first bar) and `setlist_2026.txt`. Below 1024px the library and sheet are alternate screens (`body.rj-sheet-active`), so sidebar steps leave the sheet through its own back button first. `mixer.setOpen(bool)` and `inspiration.setOpen(bool)` exist for this. **On start** the tour snapshots the visitor's tab, open song, drawer and comping value, stops audio and exits full screen; **on any end** (Done, Skip, Esc) it restores them (their own song is reopened; with none of their own the demo stays open on desktop, and on a phone the list comes back). A step whose target doesn't exist on this song (a tune without chords has no iReal Pro button; YouTube blocked, so the loop bar never appears) is skipped in whichever direction you're walking, and the "2/5" counter counts only shown steps.
- **Overlay mechanics**: `#rjTour` is `pointer-events: none` at the root (it must not cover the shield's hole); inside it, a visual `veil` and a click-eating `shield` are both full-screen with a `clip-path: polygon(evenodd …)` hole around the target (`spotlightClipPath`) — clipped-away regions take no pointer events, so on `interactive` steps ("try it": Key, Tempo, Comping) the shield's hole lets clicks through to the real control, and on every other step the shield has no hole and blocks the page. z-index 50, above the modal's 40. Wide screens float the card beside its target (`placeTooltip`: below → above → right → left → centre); ≤1024px it docks along the bottom edge — or the top edge when the target is in the lower half of the screen (the mixer bottom sheet, the floating player) — and `dockScrollDelta` scrolls the page so the target clears it.
- **The tour owns the keyboard while open** (a capture-phase `document` keydown handler): Escape ends it *before* the mixer / full screen / setlist modal see the same Escape; ←/→ step; Tab is trapped in the card; Space, ↑/↓, `/`, Enter are kept from the page's own shortcuts (Space would toggle playback, ↑/↓ step through an open setlist). On an `interactive` step the page's keys are left alone unless focus is on the card. Clicks inside the tour stop at `#rjTour` so they don't reach the mixer's document-level "click outside to close" listener.

### Static assets layout
- `static/songs/` — ABC notation files (one per song)
- `static/setlists/` — plain-text setlist files (one per band setlist) + `index_of_setlists.txt` manifest
- `static/script/` — All JavaScript. `songs-page.js` / `agenda-page.js` are the two `type="module"` entry points; vendored `abcjs*`, `tonal*` and `lamejs-1.2.1-min.js` bundles are loaded as classic scripts before them (globals `ABCJS` / `Tonal` / `lamejs`).
  - `static/script/lib/` — pure, side-effect-free ES modules (DOM micro-toolkit, instrument table, chord parsing, comping generation, iRealPro URL building, song-index/setlist-file parsing, music theory, tempo↔warp maths, setlist traversal/export metadata, personal-setlist storage, YouTube and Spotify URL/embed parsing, show-list parsing, touch-swipe classification, guided-tour copy parsing and layout maths, preferences), each with a colocated `*.test.js`. **This is where new pure logic belongs.**
  - `static/script/songs/` — the `/songs/` page orchestration: DOM + ABCjs, one module per concern, wired by `app.js` through a shared `ctx`. jsdom-tested via colocated `*.test.js`.
  - `tests/` — the jsdom harness (`helpers/dom.js` + `fixtures/songs-page.html`), shared ABCjs/Tonal/YouTube stubs (`helpers/stubs.js`) and a `ctx` builder (`helpers/ctx.js`).
- `assets/css/split.css` — Theme overrides/customizations. Unlike everything else under `static/`, this lives in Hugo's `assets/` pipeline dir (not `static/assets/`) so [layouts/partials/head.html](layouts/partials/head.html) can run it through `resources.Get | minify | fingerprint` — ~163KB source down to ~72KB minified, served from a content-hashed `/css/split.min.<hash>.css` URL with a matching `integrity` attribute, so it's cacheable indefinitely and busts automatically on every content change. Edit the file in place same as before; the hash and minification happen at build time, nothing to run by hand.
- `static/tour/` — the guided tour's copy: `tour.{en,nl,de}.md` (see **Guided tour** above)
- `static/agenda/` — Event data files

### CI/CD
GitHub Actions ([.github/workflows/publish.yaml](.github/workflows/publish.yaml)) runs on every push and every pull request, in three gated jobs (a `concurrency` group cancels superseded runs on branches/PRs but never a `master` run mid-deploy):
1. `lint-and-test` — `npm ci` (with `setup-node` npm cache), `npm run lint`, `npm test`, `npm run audit`
2. `build` (needs `lint-and-test`) — builds with Hugo via `lowply/build-hugo@v0.164.0`, runs linkchecker and `scripts/lint-seo.js` on the output, uploads `public/` as an artifact
3. `publish` (needs `build`) — whole job gated `if: github.ref == 'refs/heads/master'`: downloads that artifact and publishes it to `red-jackets-jazzband/red-jackets-jazzband.github.io` using secret `GH_RJ_DEPLOY`
